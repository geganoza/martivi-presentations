# Designer interview round — booking page design

**Date:** 2026-08-07 (Georgia time)
**Round:** Junior Graphic Designer · MARTIVI DIGITAL · Mon 2026-08-10 + Tue 2026-08-11
**Status:** approved, ready for implementation planning

---

## Problem

Ten shortlisted designers need interview slots. The `booking-page` module already solves this — it
ran the Project Assistant round on 2026-08-03 without incident — so this is a reuse, not a build.

Two things make it not a pure copy: the role belongs to **MARTIVI DIGITAL**, not Consulting, so the
candidate-facing surface must carry the Digital brand; and the page has to be reachable under
`martiviconsulting.com`, which is where the proxy infrastructure already lives.

## Goals

1. Ten named designers can each book one interview slot on Mon 10 or Tue 11 August.
2. No double-booking, ever — the guarantee the module already provides.
3. The candidate sees MARTIVI DIGITAL, the brand they applied to.
4. Nothing about the existing deployment breaks beyond the accepted consequence below.

## Non-goals

- No co-host / multi-interviewer availability this round (decided: skip — see *Deferred*).
- No changes to the API's signing, verification or booking logic.
- No new Vercel project, no new Google Calendar credentials.
- No changes to the 37 other designer applicants' records.

---

## Accepted consequence

`BOOKING_ROSTER` and `BOOKING_DAYS` are **global env vars on the deployment** — the token is only
`candidateId.signature` and carries no round identifier, so one deployment serves exactly one round.
Repointing the env to the designer round therefore makes the Project Assistant links stop resolving:
those candidate ids leave the roster, so their tokens fail verification and return 403.

This is fine — that round closed on 2026-08-05 — and it was explicitly accepted. Existing PA bookings
remain on the calendar untouched; only the links die. The `/interview` page stays reachable and simply
goes inert, by decision.

### Routing

```
martiviconsulting.com/interview/designer/?t=<token>
   → rewrite → martivi-presentations.vercel.app/interview/designer
        page → GET  /interview/api/slots?t=…   → rewrite → …/api/slots
             → POST /interview/api/book        → rewrite → …/api/book
```

**The rewrites must be inserted ABOVE the existing `/interview/:path((?:.*))` catch-all** in
`vercel.json`. That catch-all collapses everything under `/interview` onto the Project Assistant page;
a rule placed after it is dead. Add:

```json
{ "source": "/interview/designer/", "destination": "https://martivi-presentations.vercel.app/interview/designer" },
{ "source": "/interview/designer",  "destination": "https://martivi-presentations.vercel.app/interview/designer" }
```

**The page must call the API by absolute path — and the existing page already does.** `index.html:317`
reads:

```js
var API = location.hostname.endsWith("martiviconsulting.com") ? "/interview/api" : "/api";
```

That host check is load-bearing and must survive the fork verbatim. The API rewrites exist only at
`/interview/api/*`, so a relative `fetch("api/slots")` from a page at `/interview/designer/` would
resolve to `/interview/designer/api/slots` — no rewrite, silent 404. This is therefore a **regression
risk, not a gap**: do not "simplify" that ternary. It is also invisible in local testing, because
locally the hostname is not `martiviconsulting.com` and the `/api` branch is correct.

## Verification

Before a single real invitation is sent:

1. Mint a token for a throwaway id and load `/interview/designer/?t=…` through
   `martiviconsulting.com` — not the Vercel URL — so the rewrites are exercised.
2. Confirm the grid matches the real calendar, and that a slot blocked in Google does not appear.
3. Book one slot. Confirm the event lands with a Meet link, and that the slot disappears from a second
   token's grid.
4. Re-open the same token: the booked slot must still be selectable for that person (the reschedule path).
5. Confirm a tampered token returns 403.
6. Delete the test event and confirm the slot returns.
7. Confirm `/interview/` (Project Assistant) still loads and its old tokens 403 — the expected inert state.

## Deferred

- **Co-host availability.** `BOOKING_COHOSTS` exists in the module but not in the deployed
  `MARTIVI-Presentations/api/`, which is a real divergence. Skipped for this round: the investigation
  found Ujma's tenant calendar contains nothing not already on the host's, suggesting his real schedule
  lives on an account outside the tenant, so the feature would protect nothing today.
- **Round-aware tokens.** Making the token carry a round id would let rounds run concurrently and remove
  the accepted consequence above. Correct long-term fix; not needed for a single round starting Monday.
